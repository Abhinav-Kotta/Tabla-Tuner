Build a complete end-to-end MVP of a browser-based **Dayan Tabla Tuner**.

The application helps a tabla player evenly tune the dayan to a selected musical note. Unlike a normal chromatic tuner, this application should measure the pitch at multiple locations around the tabla head and create a spatial heat map showing which parts of the tabla are sharp, flat, or correctly tuned.

The final application should be functional, polished, readable, and tightly scoped to the MVP described below.

Do not add unrelated features.

# 1. PRODUCT GOAL

A tabla player should be able to:

1. Open the website on a desktop browser.
2. Upload a top-down photograph of their dayan.
3. Have the application automatically detect the tabla head and crop/normalize the image.
4. Select a target musical note.
5. Grant microphone access.
6. Be guided through 8 tuning regions around the tabla.
7. Strike each region 3 times.
8. Have each strike analyzed automatically.
9. Estimate the pitch for each strike.
10. Average the valid strikes for each region.
11. Compare each region against the selected target note.
12. See an 8-region heat map.
13. Toggle between:

* an abstract heat map
* a heat map overlaid directly on their tabla photo

14. Hover over regions to inspect tuning details.
15. See the same information in a compact table / inspector panel.
16. Receive tuning guidance such as:

* "Region 3 is sharp by 11 cents. Lower tension in this region."
* "Region 6 is flat by 8 cents. Increase tension in this region."

17. Re-measure any individual region after making adjustments.
18. Continue until every region falls inside the desired tuning tolerance.
19. See a subtle "Dayan Tuned" completion state once every region is within tolerance.

This MVP supports **dayan only**.

Do not implement bayan tuning.

Try to identify:

* outer drum-head boundary
* approximate center
* radius
* syahi / central black area if useful

The key requirement is detecting the outer circular/elliptical drum-head boundary.

Use conventional computer vision.

Possible approach:

image upload
→ resize for processing
→ grayscale
→ contrast normalization
→ blur if needed
→ edge detection
→ contour detection
→ circle/ellipse scoring
→ identify strongest tabla-head candidate

# 7. DEFINE 8 TUNING REGIONS

Divide the detected drum head into 8 equal angular tuning regions.

Approximate positions:

1. 12:00
2. 1:30
3. 3:00
4. 4:30
5. 6:00
6. 7:30
7. 9:00
8. 10:30

Represent these as angular sectors or angular strike regions.

Do NOT divide the image into rectangular blocks.

Each region should be mathematically defined relative to:

* tabla center
* tabla radius
* angular span

The strike target should be toward the outer playing/tuning portion of the dayan, not over the center syahi.

The region overlay should scale correctly if the image size changes.

# 8. TARGET NOTE SELECTION

Ask the user to select the desired target note.

C3 through B4

Examples:

C3
C#3
D3
D#3
E3
...
C4
C#4
D4
...
B4

Use A4 = 440 Hz equal temperament.

Calculate target frequency mathematically.

Do not hardcode every frequency if a clean formula can be used.

Formula conceptually:

frequency = 440 × 2^((midiNote - 69) / 12)

# 9. MAIN TUNING WORKFLOW

After setup:

* display the tabla prominently
* highlight Region 1
* activate measurement mode

Show:

"Region 1"

"Strike the highlighted area 3 times."

Once microphone permission is granted, the app should listen continuously during measurement mode.

The user should NOT need to press Record before every hit.

For each valid strike:

1. Detect the onset.
2. Capture a short useful section of the sound.
3. Estimate the pitch.
4. Validate the pitch confidence.
5. Accept or reject the strike.
6. Update the counter.

Show:

1 / 3

then:

2 / 3

then:

3 / 3

After 3 valid strikes:

* calculate the robust average pitch for that region
* calculate the nearest musical note
* calculate cents deviation from the selected target
* store the result
* automatically move to the next region

Repeat until all 8 regions are complete.

# 11. AUDIO / DSP ARCHITECTURE

This is one of the most important parts of the MVP.

Tabla produces strong harmonics.

DO NOT simply find the strongest FFT peak and call that the fundamental pitch.

A louder second harmonic could otherwise cause an octave error.

For example, if spectral peaks are:

277 Hz
554 Hz
831 Hz
1108 Hz

the algorithm should attempt to identify approximately 277 Hz as the fundamental even if the 554 Hz component is louder.

Use a readable DSP pipeline.

Suggested flow:

microphone input
→ signal buffer
→ onset detection
→ extract analysis window
→ apply window function
→ fundamental estimation
→ harmonic validation
→ confidence calculation
→ pitch result

Possible techniques:

* normalized autocorrelation
* autocorrelation
* YIN-style logic if implemented simply
* harmonic product spectrum
* FFT harmonic scoring
* combination of time-domain and frequency-domain evidence

Prefer an understandable robust algorithm rather than a very sophisticated research implementation.

The goal is reliable tuning accuracy in a quiet room.

# 14. ONSET DETECTION

Detect isolated tabla strikes.

The expected environment is:

* quiet room
* one tabla
* user striking one region at a time

A simple energy/RMS based onset detector is acceptable.

Possible behavior:

* monitor short RMS windows
* establish background noise floor
* detect sudden amplitude rise
* trigger an onset
* apply short cooldown after each onset

The cooldown should prevent one tabla strike from being counted more than once.

Tune thresholds so normal room noise does not trigger measurements.

# 15. PITCH ANALYSIS WINDOW

Do not estimate pitch from the immediate attack transient alone.

The initial attack can contain substantial broadband noise.

After detecting an onset, analyze a short section shortly after the attack where the resonant modes are clearer.

Use a reasonable delay/window.

Keep these values defined as constants with comments so they are easy to tune later.

# 16. PITCH CONFIDENCE

Pitch detection should return something like:

{
frequency,
confidence
}

Reject low-confidence estimates.

Do not pretend uncertain measurements are valid.

If confidence is too low:

"Pitch unclear. Strike again."

The exact confidence formulation can be based on:

* normalized autocorrelation peak
* harmonic agreement
* spectral consistency

# 17. THREE-STRIKE VALIDATION

Each region requires exactly 3 valid consistent strikes.

Do not blindly average three values.

Example:

294 Hz
295 Hz
440 Hz

The 440 Hz result should not be allowed to distort the region average.

Implement simple robust validation.

Possible method:

* convert frequency differences to cents
* compare each measurement to the current median
* reject strikes whose deviation from the median is above a reasonable threshold

If a strike is rejected, do not increment the 3-hit counter.

Ask the user to strike again.

Once there are 3 mutually consistent values, calculate a robust average.

A median or trimmed/weighted average is acceptable.

# 18. MUSIC THEORY UTILITIES

Implement:

frequencyToMidi

midiToFrequency

frequencyToNoteName

noteNameToFrequency

centsDifference

Use:

cents = 1200 × log2(measuredFrequency / targetFrequency)

Signed interpretation:

positive = sharp

negative = flat

Examples:

+7¢ = 7 cents sharp

-9¢ = 9 cents flat

Round values appropriately for readability.
